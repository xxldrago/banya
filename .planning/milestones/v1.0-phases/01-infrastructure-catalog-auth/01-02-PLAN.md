Create src/modules/auth/token.service.ts using the jose library (per RESEARCH.md lines 368-390):
- signAccess(userId, role): returns new SignJWT({ sub: userId, role }).setProtectedHeader({ alg: 'HS256' }).setIssuedAt().setExpirationTime('15m').sign(secret) — secret from env.JWT_SECRET (TextEncoder)
- signRefresh(userId): returns new SignJWT({ sub: userId, type: 'refresh' }).setProtectedHeader({ alg: 'HS256' }).setIssuedAt().setExpirationTime('7d').sign(secret) — secret from env.JWT_REFRESH_SECRET. Also generates a random jti (crypto.randomUUID()) for DB tracking.
- verifyAccessToken(token): uses jwtVerify from jose with JWT_SECRET, returns payload or throws
- verifyRefreshToken(token): uses jwtVerify with JWT_REFRESH_SECRET, returns payload (including jti) or throws
- Cookie constants: ACCESS_COOKIE_NAME = 'access_token', REFRESH_COOKIE_NAME = 'refresh_token'. Cookie options: access — { httpOnly: true, secure: process.env.NODE_ENV === 'production', sameSite: 'lax', path: '/', maxAge: 900 }; refresh — { httpOnly: true, secure: true, sameSite: 'lax', path: '/api/v1/auth', maxAge: 604800 }. The refresh cookie is scoped to /api/v1/auth so it is only sent to auth endpoints, reducing attack surface.

Create src/modules/auth/auth.schema.ts with zod schemas:
- registerSchema: { email (email format), password (min 8 chars), name? }
- loginSchema: { email, password }
- refreshTokenSchema: { refreshToken? } — reads from cookie or body

Create src/modules/auth/auth.service.ts with:
- register({ email, password, name? }): validate with registerSchema, check if email exists (prisma.user.findUnique), hash password with argon2 (argon2.hash(password)), create user with role CLIENT, call signAccess + signRefresh, persist refresh token in DB (prisma.refreshToken.create with jti, userId, expiresAt = now + 7d), return { user: { id, email, role }, accessToken, refreshToken }
- login({ email, password }): validate, find user by email, verify password with argon2.verify, check user.status === 'active', sign tokens, persist refresh, return { user, accessToken, refreshToken }
- refresh(refreshToken): verify with verifyRefreshToken, check DB for token by jti where revokedAt is null and expiresAt > now, if not found throw Unauthorized('TOKEN_REVOKED'), revoke old token (prisma.refreshToken.update set revokedAt = now), sign new access + new refresh, persist new refresh, return { accessToken, refreshToken }
- logout(refreshToken): verify, find by jti, revoke (set revokedAt = now), return void
- getCurrentUser(userId): prisma.user.findUnique with select excluding passwordHash, return or throw Unauthorized

Create src/shared/middlewares/get-session.ts with getSession(req): extracts access_token from cookie (using next/headers cookies() for server components / req.cookies for route handlers), calls verifyAccessToken, returns user payload or null. This is the non-throwing variant.

Create src/shared/middlewares/require-auth.ts with requireAuth(req): calls getSession, if null throws Unauthorized (401). Returns the user object. This is the throwing variant for protected endpoints.

Create src/shared/middlewares/require-role.ts with requireRole(roles: Role[]) returning a function(user: User) that checks roles.includes(user.role), throws Forbidden (403) if not. Usage pattern: `const user = await requireAuth(req); requireRole(['PARTNER'])(user);`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → /api/v1/auth/* | Untrusted credentials cross here (register, login) |
| Client → Protected routes | Access token cookie verified at middleware + route handler |
| Refresh endpoint → Token DB | Refresh token rotation: old token revoked, new issued atomically |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-04 | Spoofing | /api/v1/auth/login | high | mitigate | Rate limiting on login attempts (in-memory counter per IP+email, block after 5 failures / 15 min); argon2 password verification; constant-time comparison |
| T-01-05 | Information Disclosure | Refresh tokens | high | mitigate | HttpOnly + Secure + SameSite=Lax cookies (not accessible via JS); refresh cookie scoped to /api/v1/auth path; short-lived access (15m) limits exposure window |
| T-01-06 | Tampering | JWT tokens | high | mitigate | jose library with HS256 signature verification — tampered tokens fail verification; separate secrets for access (JWT_SECRET) and refresh (JWT_REFRESH_SECRET) |
| T-01-07 | Elevation of Privilege | RBAC middleware | high | mitigate | requireRole checks user.role against allowed roles array; ownership checks (partnerId == user.partner.id) on resource access — prevents IDOR |
| T-01-08 | Repudiation | Refresh token rotation | medium | mitigate | Each refresh token has unique jti stored in DB; old token revokedAt set on rotation; audit trail of issued/revoked tokens |
| T-01-09 | Spoofing | Token theft / replay | high | mitigate | Refresh token rotation detects theft (old token revoked, attacker's next refresh fails); 7d expiry limits replay window |
| T-01-SC | Tampering | npm installs (jose, argon2) | high | mitigate | Both jose and argon2 are well-established, high-download packages confirmed in RESEARCH.md standard stack — no blocking checkpoint needed |
</threat_model>
